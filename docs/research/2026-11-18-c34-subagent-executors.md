## Вопрос 1. Субагенты Cursor

Источник, если ниже не назван другой: [Subagents](https://cursor.com/docs/subagents), чтение 18.11.2026.

### Запись файлов

- Субагент — отдельное контекстное окно. Родитель поручает работу и получает результат обратно. [факт: Subagents, 18.11.2026]
- Поле `readonly` по умолчанию `false`. При `readonly: true` нет правок файлов и нет shell-команд, меняющих состояние. [факт: Subagents, таблица полей, 18.11.2026]
- У хука `subagentStop` во входе есть `modified_files` — файлы, которые субагент изменил. [факт: Hooks](https://cursor.com/docs/hooks), чтение 18.11.2026
- Страница Subagents не называет инструмент записи по имени. То, что при `readonly: false` запись в репозиторий разрешена, следует из запрета правок только в режиме `readonly` и из поля `modified_files`. [вероятно]
- В этом репозитории единственный проектный субагент — `.cursor/agents/verifier.md`: `readonly: true`, git не запускает. [факт: файл, разбор 18.11.2026]

### Shell

- Ограничение «нет shell-команд, меняющих состояние» страница даёт только для `readonly: true`. [факт: Subagents, 18.11.2026]
- Отдельной фразы «субагент с `readonly: false` имеет shell» на странице нет. [факт: страница молчит, 18.11.2026]
- Субагенты наследуют инструменты родителя, включая MCP. Исключение — облачный субагент: у него MCP команды с cursor.com/agents, не локальный. [факт: Subagents, FAQ, 18.11.2026]
- Страница CLI говорит, что агент CLI умеет файлы, поиск, shell и веб. Это агент CLI, не описание редакторского субагента. [факт: Using Agent in CLI](https://cursor.com/docs/cli/using), чтение 18.11.2026
- Вывод «редакторский субагент без readonly выполняет shell» — [вероятно]. Требует ручной проверки. В этой задаче не проверялось.

### Рабочий каталог

- По умолчанию субагенты делят checkout родителя. Одновременная правка одних и тех же файлов может затирать изменения друг друга. [факт: Subagents, «Isolated project copies», 18.11.2026]
- Изоляцию просят текстом. Тогда у субагента своя среда и своя ветка: изолированный git worktree со своим рабочим каталогом на той же машине, либо облачная VM со своим клоном. Изменения остаются на ветке субагента, пока родитель не соберёт результат. [факт: Subagents, 18.11.2026]
- В конфигурации субагента перечислены `name`, `description`, `model`, `readonly`, `is_background`. Поля каталога или пути клона нет. [факт: Subagents, таблица полей, 18.11.2026]

### Можно ли указать уже существующий клон

- Страница Subagents не описывает параметр «работать в `../<repo>-<cxx>`». Изоляция создаёт новый worktree или облачный клон, а не принимает путь существующего клона. [факт: Subagents, 18.11.2026]
- Страница Worktrees описывает checkout агента, `.cursor/worktrees.json`, `/worktree`, `/best-of-n` и автоочистку. Отдельный клон рядом с репозиторием она не упоминает. [факт: Worktrees](https://cursor.com/docs/configuration/worktrees), чтение 18.11.2026
- Можно ли текстом запроса заставить редакторского субагента открыть уже существующий клон — страница не говорит. Требует ручной проверки. Не проверялось.
- У CLI другой рычаг: без `--workspace` берётся текущий каталог; `--workspace` задаёт корень; `--worktree` создаёт новый worktree под `~/.cursor/worktrees/`, а не указывает готовый клон. [факт: Using Agent in CLI, 18.11.2026]

### beforeShellExecution

- В `.cursor/hooks.json` зарегистрирован только `beforeShellExecution`, `failClosed: true`, команда `scripts/hooks/guard-git.ps1`. Хуков `subagentStart` / `subagentStop` нет. [факт: файл, разбор 18.11.2026]
- Страница Hooks относит `beforeShellExecution` к хукам Agent Chat и пишет: вызов перед любой shell-командой. Во вход входят `command`, `cwd`, `sandbox`. Проектный хук запускается из корня проекта в доверенном workspace. [факт: Hooks, 18.11.2026]
- `subagentStart` и `subagentStop` описаны отдельно. У `subagentStart` во входе есть `git_branch` и `is_parallel_worker`. Страница не пишет, что shell субагента проходит `beforeShellExecution`. [факт: Hooks молчит об этой связи, 18.11.2026]
- Срабатывает ли guard на shell субагента — требует ручной проверки. Не проверялось. Пока это не проверено, считать покрытие guard доказанным нельзя.

### Лимиты параллели

- Несколько вызовов Task в одном сообщении родителя запускают субагентов одновременно. Числового потолка страница Subagents не даёт. [факт: Subagents, «Parallel execution», 18.11.2026]
- Пример стоимости: пять субагентов параллельно тратят примерно в пять раз больше токенов, чем один агент. Это пример, не лимит. [факт: Subagents, 18.11.2026]
- Вложенность: с Cursor 2.5 субагент может запустить дочернего, а тот — уже нет. [факт: Subagents, FAQ, 18.11.2026]
- `loop_limit` у `subagentStop` по умолчанию 5. Это предел автоматических продолжений, не предел одновременных субагентов. [факт: Hooks, 18.11.2026]
- `cursor.worktreeMaxCount` по умолчанию 25 на машину. С Cursor 3.5 в очистку попадают и каталоги, созданные вне менеджера, включая `git worktree add`. Это предел хранимых worktree, не предел субагентов. [факт: Worktrees, 18.11.2026]
- Числового лимита «не больше N субагентов сразу» прочитанные страницы не содержат.

Облачные субагенты страница описывает (`/in-cloud`, своя VM и ветка). Бриф этой задачи их не рассматривает как вариант. В таблицу рекомендуемым рядом они не входят.

## Вопрос 2. Альтернативы

### Отдельные Issue

- Сейчас цикл уже такой: задачи по очереди в основном checkout; параллельная задача — отдельный клон `../<repo>-<cxx>` и одно окно Cursor; ветка только в одном клоне. [факт: `protocol/cycle.md`, раздел «Рабочий каталог», разбор 18.11.2026]
- Публикация одной согласованной задачи: commit, push ветки, один pull request. Merge делает Perplexity, не Cursor. [факт: `protocol/roles.md`, `protocol/cycle.md`, разбор 18.11.2026]
- Дробление одной задачи на несколько Issue в `cycle.md` не описано. [факт: в прочитанном `cycle.md` такого раздела нет, 18.11.2026]
- Если каждая подзадача — своё Issue, свой клон, своя ветка и свой PR, очередь merge остаётся ручной: один handoff и один SHA на ревью. Это совпадает с правилом «одна задача — одна ветка — один PR» в том виде, как его формулирует тело Issue #60. В `cycle.md` этой фразы дословно нет: там одна ветка на клон и один проход цикла до PR. [факт: Issue #60 и `cycle.md`, 18.11.2026]
- Такой контур не требует пишущего субагента. Guard тот же, что у обычного окна: в клоне лежат те же `.cursor/hooks.json` и `scripts/hooks/guard-git.ps1`, если клон снят с этого репозитория. [факт: файлы репозитория, 18.11.2026] Живой обход #59 при этом никуда не девается. См. вопрос 5.

### Cursor CLI / headless в клонах

- `agent --workspace <каталог>` запускает агента в указанном корне. Запуск из каталога клона без флага использует текущий каталог. [факт: Using Agent in CLI, 18.11.2026]
- `--print` — неинтерактивный режим. Он правит файлы workspace и выполняет уже разрешённые команды без вопроса. То, что потребовало бы подтверждения, отклоняется, если не передан `--force`. `--force` выполняет действия без подтверждения, кроме `permissions.deny` и политик команды. [факт: Using Headless CLI](https://cursor.com/docs/cli/headless), чтение 18.11.2026; то же в Using Agent in CLI, 18.11.2026
- Пример установки headless задаёт `CURSOR_API_KEY`. Страницы CLI, прочитанные 18.11.2026, не сравнивают счёт IDE-сессии и счёт CLI. Платный это контур или нет — страницами не сказано.
- Прочитанные страницы CLI не пишут, что `agent` загружает `.cursor/hooks.json` и гоняет `beforeShellExecution`. Страница Hooks прямо говорит это про cloud agents и про открытый доверенный workspace, не про CLI. [факт: Hooks и CLI, 18.11.2026] Требует ручной проверки. Не проверялось.
- `--worktree` у CLI создаёт worktree Cursor, не отдельный клон протокола. Автоочистка общая с редактором, предел `cursor.worktreeMaxCount`. [факт: Using Agent in CLI и Worktrees, 18.11.2026]

## Вопрос 3. Сборка без git merge у Cursor

- Cursor не выполняет merge и не включает auto-merge. Merge в `main` делает ревьюер по SHA из handoff. [факт: `protocol/roles.md`, `protocol/verdict.md`, разбор 18.11.2026]
- `guard-git.ps1` на глагол `merge` у git отвечает deny («git merge is blocked for Cursor (ADR-0003)»). Так устроен разбор скрипта. Живой прогон в этой задаче не делался. [факт: разбор `scripts/hooks/guard-git.ps1`, 18.11.2026]
- В том же файле строки `rebase` нет. Значит ли это allow в живом Cursor — требует ручной проверки. Не проверялось. Force-push в ходе задачи запрещён `protocol/platform.md`. [факт: разбор скрипта и `platform.md`, 18.11.2026]
- Сборка, которая не вызывает `git merge` у Cursor: у каждой подзадачи свой PR, Perplexity мёржит по очереди. Это действие ревьюера на GitHub, не shell Cursor. [факт: `protocol/roles.md`, 18.11.2026]
- Git часто сливает ветки сам, если правки на разных строках или в разных файлах. Конфликт типичен, когда одна и та же строка одного файла изменена по-разному, или один файл правят, а другой удаляют. Пока конфликт есть, кнопка merge на GitHub неактивна. Пример локального разрешения в документации — `git merge`, то есть команда, которую guard у Cursor режет. [факт: Merge conflicts](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/addressing-merge-conflicts/about-merge-conflicts), чтение 18.11.2026; факт про deny — разбор guard, 18.11.2026
- Правило непересекающихся файлов снижает шанс конфликта. Оно не гарантирует чистый merge: расхождение базы и удаление файла документация тоже считает конфликтом. [вероятно]
- Ребейз второй подзадачи после merge первой переписывает уже отправленную ветку. Обычный запрет force-push в `platform.md` такой push не разрешает. Кто имеет право ребейзить — в протоколе не назначено. [факт: `platform.md` запрещает force-push, 18.11.2026; назначение роли — в прочитанных `roles.md` и `cycle.md` этого нет]
- Формулировка Subagents «родитель собирает результаты» с веток субагентов — другой механизм. Кто выполняет этот сбор, страница не сводит к pull request и ревьюеру. [факт: Subagents, 18.11.2026] Совместить это с запретом merge у Cursor без новой правки `roles.md` нельзя. [вероятно]

## Рекомендация

Не брать пишущих субагентов. Документация не даёт им путь в уже существующий клон, изоляция — worktree или облако, сбор результата описан как действие родителя, а прохождение shell через `beforeShellExecution` не подтверждено.

Не брать CLI / headless в клонах. Прочитанные страницы не подтверждают guard, а `--force` и `--print` ослабляют подтверждения.

Целевая схема дробления, если она понадобится после закрытия #59: отдельные Issue, каждый в своём клоне и окне, со своим PR и ревью Perplexity, плюс правило непересекающихся файлов. Ребейз второй ветки и force-push этим исследованием Cursor не разрешаются — это отдельное решение владельца (кандидат 2).

До закрытия #59 не открывать параллельные пишущие окна. Пока владелец не выбрал иное, остаётся текущий порядок: одна задача в основном checkout.

Выбор за владельцем. Этот документ решение не подменяет.
