# Синхронизация закреплённого коммита

Workflow потребителя запускается по `workflow_dispatch` и по расписанию `17 6 * * 1`. Он открывает pull request. В default branch напрямую он не пушит и automerge не включает.

## Что считается доверенным

Скрипты берутся из уже закреплённого сабмодуля и копируются во временный каталог до переключения на ветку обновления. После этого workflow не запускает `scripts/` из нового SHA.

Новые файлы читаются через `scripts/export-protocol-data.mjs`. Перед записью скрипт смотрит `git ls-tree` выбранного SHA. В `protocol/`, `schemas/` и `templates/` допускаются только обычные файлы режимов `100644` и `100755`. Symlink, gitlink и путь с `..` или абсолютным префиксом отклоняются до извлечения; при отказе каталог назначения не меняется. Чтение этих данных и запись адаптеров дополнительно не проходят через symlink файла или любого родительского каталога.

## Когда pull request не создаётся

- Закреплённый SHA уже равен SHA default branch протокола.
- Закреплённый SHA не является предком целевого коммита. Так workflow не откатывает pin на более ранний `main` и не прыгает в сторону.
- Повторный запуск не находит содержательной разницы.
- Уже есть открытый pull request из ветки `chore/sync-agentic-protocol`: новый коммит пушится в неё обычным push, без второй заявки и без force-push.

## Разрешения

У job только `contents: write` и `pull-requests: write`. Общий default permissions репозитория этот workflow не повышает. Секретов в репозитории и в тексте pull request нет: используется встроенный `GITHUB_TOKEN`.

Если этот токен не может создать pull request, журнал должен назвать настройку, а не просить прислать личный токен:

`Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests`.

Пока настройка выключена, запись ветки может быть доступна отдельно от создания pull request. Настройку включает владелец репозитория.
